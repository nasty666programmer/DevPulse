The Hidden Cost of Premature Abstraction

Every codebase has that one interface with a single implementation, built "for flexibility later." Later rarely comes — and when it does, the abstraction is usually wrong for the new case anyway, so it gets bypassed or ripped out.

The author argues for a simple discipline: write the concrete thing twice before you extract an abstraction. Duplication is cheap to delete; the wrong abstraction is expensive to unwind, because by the time you notice it's wrong, four other modules already depend on its shape.

There's a good concrete example in the piece — a payments module that grew a PaymentStrategy interface for a single provider, then had to grow three more interfaces just to shoehorn a second provider into the original shape instead of adapting the abstraction itself.

Takeaway that stuck with me: abstractions should be discovered from real duplication, not designed in anticipation of it.
